MULTIRATER — Interview Prep

A complete guide to discussing this project for a Staff Engineer role. Know it inside out.

2-Minute Pitch

MULTIRATER is a hybrid media recommendation system I built as my final year BE project, which was published in IJRASET (Paper ID: IJRASET42927). It recommends movies, songs, and books using different ML algorithms tailored to each domain — collaborative filtering for movies and books, audio-feature-based KNN for songs. The stack is React 17 + Flask with pre-processed CSV datasets. The core insight of the project is that different content types benefit from fundamentally different recommendation strategies, and applying one-size-fits-all algorithms produces inferior results.

General Questions
Q
What is MULTIRATER and what problem does it solve? ▼

MULTIRATER is a multi-domain media recommender — it recommends movies, songs, and books from a single unified interface. The user rates a few items they know, and the system generates personalized recommendations.

The problem it solves is cold-start personalization: rather than requiring a long history, the user just rates 1-5 items they already know and gets meaningful recommendations immediately. This is especially practical for a demo or proof-of-concept system.

Q
Why did you use different algorithms per domain? ▼

This was the core intellectual contribution of the project. The data characteristics differ fundamentally per domain:

  • Movies — Rich metadata (genres, cast, director, keywords, overview) plus dense user rating data (MovieLens). A hybrid approach combines both signals.
  • Songs — Spotify provides 12 objective numeric audio features (danceability, energy, valence, tempo, etc.) but no user ratings in our dataset. Feature-based nearest neighbor is the natural fit.
  • Books — Limited metadata, but rich user rating data (~30K Amazon users). Pure collaborative filtering (KNN on user-rating matrix) works best here.

Applying collaborative filtering to songs would fail because there's no rating data. Applying pure content-based to books would fail because text metadata alone is a poor predictor of taste. Matching the algorithm to the data type is the right engineering decision.

Q
Walk me through the user flow end-to-end. ▼
  1. User lands on / (Home) — picks a category: Movies, Songs, or Books.
  2. The category page loads 16 randomly-sampled top-rated items from the backend (GET /movies_votes, etc.).
  3. User rates known items using sliders (0–5). Ratings are stored in a useRef array — no re-renders.
  4. User clicks "Submit" → frontend validates at least one item is rated, then POST /recommendmovie with the ratings array.
  5. Backend computes recommendations, stores in a global variable, returns 201.
  6. Frontend navigates to the results page, immediately GET /movie_result.
  7. Up to 12 recommendations are displayed as cards.
Q
What was published in IJRASET and what was the research contribution? ▼

Paper ID IJRASET42927 in the International Journal for Research in Applied Science and Engineering Technology.

The research contribution was demonstrating that domain-specific algorithm selection outperforms a generic recommendation approach when building a multi-domain system. We evaluated all three recommenders manually and showed that the hybrid movie recommender benefited from the ensemble combination of content-based methods (intersection-first strategy), while songs and books were best served by purely feature-based and collaborative approaches respectively.

Q
Walk me through the system architecture. ▼

Classic two-tier architecture: React SPA frontend + Flask REST API backend. Deliberately minimal — no database, no auth, no caching layer. All data is pre-processed CSV files loaded at startup into pandas DataFrames.

The frontend proxies all API calls to Flask via CRA's "proxy": "http://localhost:5000/" in package.json, which eliminates CORS in development without requiring flask-cors.

The interesting architectural piece is the two-step recommendation pattern: client POSTs ratings to trigger computation, gets back a 201, then GETs the results. Results are held in module-level Python globals between those two calls.

Q
Why no database? Why CSV files? ▼

The datasets are static — 1,496 movies, 8,010 songs, 727 books. They don't change. Using pandas DataFrames loaded from CSVs at startup gives fast in-memory querying without ORM overhead.

Why it works here
  • Zero setup — no DB server needed
  • Fast in-memory queries via pandas
  • Portable — clone and run
  • Appropriate for static data
Production trade-offs
  • Re-reads disk on every request
  • No online updates / learning
  • Doesn't scale horizontally
  • No query indexing
At Scale PostgreSQL for catalog, Redis for recommendation caching, a vector DB (Pinecone/FAISS) for embedding lookups.
Q
Why Flask over Django or FastAPI? ▼

Flask was the right choice here — minimal boilerplate, fast to prototype, and the project only needed 9 endpoints. Django would have been overkill (ORM, admin panel, migrations — none needed). FastAPI would have been a better production choice today (async support, built-in OpenAPI docs, Pydantic validation), but at the time Flask was more accessible for the team.

If I rewrote it today: FastAPI with Pydantic models for request/response validation and auto-generated OpenAPI docs.

Q
Why are there two CSV files for movies (movies4 and movies5)? ▼

This is a deliberate separation of concerns. The movies4_1496.csv file is the "presentation" dataset — clean display fields (title, poster URL, cast, genres). The movies5_1496.csv file adds a tags column, which is a pre-processed NLP artifact.

The tags field is a concatenation of: genres, keywords, overview words, cast names (no spaces to treat "Tom Hanks" as one token), director, and production companies — all lowercased. Sending this to the frontend would be wasteful payload, and it should never leave the backend since it's an internal ML feature.

The separation enforces the principle that ML feature engineering artifacts don't leak into the presentation layer.

Q
Why use jsonpify instead of jsonify? ▼

flask_jsonpify is a legacy CORS workaround — it wraps responses in a JavaScript callback for JSONP. This was unnecessary given the proxy in package.json.

The fact that both exist suggests the proxy was added after the backend was built. This is technical debt — all responses should use jsonify from Flask directly, and flask_jsonpify should be removed from dependencies.

Q
Describe the startup and deployment setup. ▼

I wrote cross-platform start.sh / stop.sh bash scripts. start.sh:

  1. Detects OS (macOS / Windows / Linux)
  2. Checks and installs npm packages (npm install) and Python venv + pip requirements
  3. Launches two terminal tabs — one for npm start (React on :3000), one for python3 -m flask run (Flask on :5000)
  4. Supports iTerm2, Terminal.app, Windows Terminal, gnome-terminal, xterm

stop.sh kills processes on ports 3000 and 5000 using lsof on macOS/Linux or netstat/taskkill on Windows.

Modern Alternative Docker Compose with two services (node, python) would be more reproducible and eliminate OS detection complexity.
Recommendation Algorithms

Movies — Hybrid (Collaborative + Content-Based)

Movie.py
1

Collaborative Filtering (Pearson Correlation): Pre-computed 1,496×1,496 correlation matrix. For each rated movie, multiplies its correlation vector by (rating - 2.5). The 2.5 offset means ratings above midpoint add positive signal, below add negative signal. Sum all weighted vectors, sort, exclude rated movies → collab candidate IDs.

2

Content-Based — Dual method (only for rating ≥ 3):

• CountVectorizer + Cosine Similarity: Bag-of-words on tags column, max_features=1000, stop_words='english'

• TF-IDF + Sigmoid Kernel: TfidfVectorizer(min_df=3) on tags, sigmoid kernel similarity matrix

• Take intersection first (both methods agree) → fill from union if needed. Sort by vote_average.

3

Merge: Combine collab IDs + content IDs, filter from full dataframe, sort by vote_average descending. Return up to 12 movies.

Songs — Feature-Based Manhattan Distance KNN

Song.py
1

For each song rated ≥ 3, calls recommendOneSong()

2

For every candidate song (all 8,010), computes Manhattan distance across 12 Spotify audio features: duration_ms, acousticness, danceability, energy, instrumentalness, key, liveness, loudness, mode, speechiness, tempo, valence

3

Sort by distance ascending, deduplicate on Spotify URL, return top 21 candidates per input song. Take first 21 IDs across all recommendations.

Known Limitation Pure Python loop over 8,010 songs — O(n) per query. Features are not normalized. A song with high duration_ms (~200,000) dominates the distance vs. features with range 0–1.

Books — Collaborative Filtering (KNN + Cosine Similarity)

Book.py
1

Uses a 673 books × ~29,783 users pivot table where values are user ratings (sparse CSR matrix).

2

For each book rated ≥ 3: look up its row in the pivot table, run it through NearestNeighbors(metric='cosine', algorithm='brute') to find K most similar books by rating pattern.

3

Collect all neighbor titles, deduplicate (keep first), sort by Avg-Rating descending → return top 12.

Q
Why pre-compute the movie correlation matrix instead of computing at runtime? ▼

The matrix is 1,496 × 1,496 = ~2.24 million values. Computing pairwise correlations from raw user-rating data at query time would be O(n²) per request. Pre-computing it offline and serializing to CSV makes query time O(n) — just a lookup and weighted sum.

The trade-off: the matrix is static and doesn't incorporate new user feedback. For production, you'd rebuild it periodically via a batch job, or use approximate nearest neighbor (ANN) methods like FAISS for sub-linear search at scale.

Q
Why the intersection-first strategy for combining two content-based methods? ▼

This is an ensemble agreement strategy. Two independently-computed representations of the same content (bag-of-words vs TF-IDF + sigmoid kernel) will naturally disagree on edge cases. Items that both methods rank highly are more likely to be genuinely similar to the query, not just an artifact of one method's biases.

Concretely: if CountVectorizer + cosine similarity recommends [A, B, C, D] and TF-IDF + sigmoid recommends [B, C, E, F], the intersection {B, C} are the "confident" recommendations. The union {A, B, C, D, E, F} minus intersection gives the "uncertain" ones used as backfill.

This is analogous to model ensemble voting — agree on the output, not just the average. It's a conservative strategy that tends to produce fewer but higher-confidence recommendations.

Q
Why Manhattan distance for songs? Why not Euclidean or Cosine? ▼

Manhattan distance is less sensitive to outliers in any single dimension than Euclidean. When features have very different scales (duration_ms ~200,000 vs valence 0–1), Euclidean distance would be dominated by the high-scale features. Manhattan reduces that domination somewhat — each dimension contributes its absolute difference rather than its squared difference.

Cosine similarity measures directional similarity — good for sparse high-dimensional text vectors. For dense numeric audio features where magnitude matters (a song with high energy is meaningfully different from a low-energy song), cosine distance is less appropriate.

Honest Reflection The right fix is feature normalization (z-score or min-max) before computing any distance metric. Without it, duration_ms dominates the distance regardless of which metric is used. This is a known limitation.
Q
What is the dead KMeans code in Song.py? Why is it there? ▼

That's the addFeaturesColumn() function — vestigial code from an earlier iteration. The original design was to pre-cluster songs into 10 KMeans clusters by audio features, then only compute distances within the same cluster. This was a pruning strategy: instead of comparing against all 8,010 songs, only compare against ~800 in the same cluster — ~10x speedup.

I moved away from it because cluster boundaries created false negatives: a song on the edge of cluster 3 might have its nearest neighbor in cluster 4, which would be completely missed. The brute-force O(n) loop was fast enough for 8,010 items and more correct.

What I'd do today Use sklearn's NearestNeighbors(metric='manhattan', algorithm='ball_tree') or numpy vectorization: np.sum(np.abs(features - query), axis=1) — ~100x faster than the Python loop.

I should have deleted the dead code before submission — this would fail a code review.

Q
Why does the (rating - 2.5) weighting work for collaborative filtering? ▼

This is the mean-centered rating trick from classical collaborative filtering. The idea:

  • Rating 5: weight = +2.5 (strong positive signal — strongly recommend similar items)
  • Rating 4: weight = +1.5 (moderate positive signal)
  • Rating 2.5: weight = 0 (neutral — no signal in either direction)
  • Rating 1: weight = -1.5 (mild negative signal)
  • Rating 0: weight = -2.5 (strong negative signal)

By multiplying a movie's correlation vector by this weight and summing across all rated movies, high-rated movies push their correlated neighbors up the recommendation list while low-rated movies push them down. It's a simple but effective way to encode preference direction into a similarity-based lookup.

Q
Why does the rating threshold for recommendations start at 3/5? ▼

Only items rated ≥ 3 are used as seeds for content-based and book/song recommendations. The reasoning: if a user rates a movie 1/5, we don't know why they disliked it. Genre aversion? Bad experience? Random noise? Using low-rated items as negative examples without understanding the reason can degrade recommendation quality.

This is a limitation: we lose negative signal. A sophisticated system (YouTube's "not interested," Spotify's thumbs-down) uses explicit negative feedback with specific weighting. For this prototype, ignoring low-rated items was the conservative safe default.

Note: the collaborative filtering step does use all ratings via the (rating - 2.5) weighting — so low ratings do have negative influence there. The threshold only applies to the content-based seeding.

Frontend Design Decisions
Q
Why useRef instead of useState for storing ratings? ▼

When a user moves a slider, useState would trigger a re-render for the entire list of 16 movie cards — that's unnecessary DOM work. Using useRef means the slider value is stored as a mutable ref (via a ref array indexed by movie ID) without causing re-renders.

We only need the rating values at one moment: when the user clicks "Submit." We don't need React to track them reactively between changes. This is a classic case where ref is semantically correct — it's not state that the UI needs to react to, it's imperative data we hold onto and read later.

Trade-off You lose reactivity. If you wanted a live counter ("You've rated 3 of 16 items"), you'd need state. For our submit-only use case, ref is the right call.
Q
Why React Router v5 instead of v6? ▼

Built in 2022 when React Router v5 was the stable production choice. v6 had just released with significant breaking API changes: Switch → Routes, component={} → element={}, useHistory → useNavigate. For a student project on a fixed timeline, staying on the version we knew well was the pragmatic call.

In a production project today, I'd use v6 or Next.js App Router with file-system based routing.

Q
Why did you use the CRA proxy instead of setting up CORS on Flask? ▼

The CRA proxy makes all API calls appear same-origin from the browser's perspective — no CORS headers needed. The alternative, flask-cors, works but requires careful configuration (wildcard origins are a security risk in production, specific origins need updating per environment).

The proxy is a dev-only convenience. In production, you'd put both services behind nginx: /api/* → Flask, everything else → React static files. Same-origin, no CORS config needed.

Q
How does the genre filter work? Walk me through the implementation. ▼

The filter is a controlled state object (e.g. { Drama: true, Thriller: false, ... }) toggled by checkboxes. A useEffect watches the filter state with a 1-second debounce via setTimeout:

useEffect(() => {
  const timer = setTimeout(() => {
    // POST /filter with genre object
    // then GET /filtered → update displayed movies
  }, 1000);
  return () => clearTimeout(timer); // cleanup
}, [filter]);

The debounce prevents a flood of API calls while the user is toggling multiple checkboxes. It waits for 1 second of inactivity before firing.

Design Flaw Filtering is a read operation — it should be GET /movies?genres=Drama,Thriller with query params, not a POST that mutates global server state. The current design is a REST anti-pattern.
Q
Why CoreUI? What did it provide? ▼

CoreUI provided ready-made components that fit the project's card-heavy UI: CCard, CModal, CBadge, CToast, CFormRange. This let us focus on ML logic rather than building UI primitives from scratch.

The main components used:

  • CFormRange — the rating sliders (0–5)
  • CModal (XL) — movie/book detail views with poster, cast, overview
  • CBadge — genre and date tags on movie cards
  • CToast — warning when user hasn't rated anything before submitting
Q
Why does the songs page show Spotify links but movies don't have a direct watch link? ▼

The Spotify dataset includes a direct url field (column index 18) pointing to the Spotify track. The Spotify icon link on each song card opens this URL directly — it's free data from the dataset.

Movies don't have streaming links because the TMDB/MovieLens dataset doesn't include them — streaming rights vary by region and platform, so TMDB deliberately doesn't expose those links. We only have poster URLs (from Amazon CDN) in the movie dataset.

Scalability & Production Readiness
Q
Global Python state for recommendations — that's a race condition, right? ▼

Absolutely. The globals movies_recommend_final, songs_recommend_final, books_recommend_final are overwritten on every POST. If User A POSTs, then User B POSTs before User A calls GET, User A gets User B's results. Classic TOCTOU (time-of-check-time-of-use) race condition.

The right fixes, in order of simplicity:

  1. Synchronous: Return recommendation results directly in the POST response body — no second GET needed at all.
  2. Job ID pattern: POST returns a UUID, client polls GET /result/{uuid}. Results stored per-job, not globally.
  3. Task queue: For long-running computation — Celery + Redis. POST enqueues a task, returns job ID. Worker computes and stores result. Client polls.
Q
How would you scale this to 10,000 concurrent users? ▼

The current architecture would fail immediately. Redesign steps:

  1. Stateless API: Remove all globals. POST returns recommendations directly. Enables horizontal scaling.
  2. Pre-computed embeddings: Store movie/book/song feature vectors in FAISS or Pinecone. Query becomes an ANN search — milliseconds, not seconds.
  3. Caching: Cache recommendation results by input fingerprint in Redis (TTL ~1 hour). Same rating pattern → cache hit, no recomputation.
  4. Horizontal scaling: Deploy Flask behind gunicorn (4+ workers) + nginx. Or containerize with Docker and scale via Kubernetes.
  5. Async workers: For heavy computation, use Celery + Redis. POST enqueues, worker computes, client polls.
  6. PostgreSQL: Replace CSV reads with indexed DB queries.
  7. CDN: Serve poster images from CDN, not Amazon direct URLs.
Q
The song recommender is a pure Python O(n) loop. How would you optimize it? ▼

Three levels of optimization:

Level 1 — Numpy vectorization (100x faster, 5 minutes to implement):

distances = np.sum(np.abs(all_features - query_features), axis=1)
indices = np.argsort(distances)[:21]

Level 2 — sklearn NearestNeighbors (sub-linear with BallTree):

nn = NearestNeighbors(n_neighbors=21, metric='manhattan', algorithm='ball_tree')
nn.fit(normalized_features)
distances, indices = nn.kneighbors([query])

Level 3 — FAISS (production, millions of items, GPU-accelerated):

Build an IVF index offline, use approximate nearest neighbor search. Query time O(log n) in practice.

Also: normalize features first (z-score per column) to prevent duration_ms dominating the distance.

Q
What testing exists? What would you add? ▼

Honest answer: No automated tests. The project used manual integration testing — run the app, rate items, verify results look reasonable.

What I'd add for production:

  • Unit tests (pytest): Known input → expected output for all three recommendation functions. Snapshot tests for edge cases (all low ratings, single rating, all same genre).
  • API integration tests: Flask test client, test all 9 endpoints. Verify 201 on POST, correct data shape on GETs.
  • Frontend component tests: React Testing Library — slider interactions, submit validation, toast rendering.
  • E2E tests: Cypress or Playwright — full user journey from rating to results.
  • Offline evaluation: Hold-out evaluation using MovieLens test split. Precision@K, Recall@K, NDCG for the movie recommender.
Q
If you rewrote this from scratch today, what would you do differently? ▼
  1. FastAPI instead of Flask — async, type hints, auto-generated OpenAPI docs, Pydantic validation
  2. Return recommendations in the POST response — eliminate global state entirely
  3. Feature normalization for songs before distance computation
  4. Sentence-transformers for movie embeddings instead of CountVectorizer (richer semantic similarity)
  5. FAISS or Pinecone for ANN search instead of brute-force loops
  6. Docker Compose instead of bash start/stop scripts
  7. Negative feedback — use low ratings as signal with explicit weighting
  8. Proper REST design — genre filter as GET with query params, not POST
  9. Delete dead code — remove the unused KMeans block in Song.py
  10. Test coverage — unit + integration + E2E from day one
Data Sources & ML Details
Q
Where did the datasets come from? ▼
  • Movies: TMDB (The Movie Database) metadata dataset. Correlation matrix derived from MovieLens user ratings data. Filtered to 1,496 movies present in both datasets.
  • Songs: Spotify Tracks Dataset (available on Kaggle, originally ~600K tracks). We used a curated subset of 8,010 songs that included audio feature data.
  • Books: Amazon Books dataset — ratings, user data, and book metadata. Filtered to 727 popular books with sufficient rating density; pivot table covers ~29,783 users.
Q
Why only 1,496 movies? Why not more? ▼

Two constraints:

1. Correlation matrix size: The matrix grows as O(n²). At 1,496 movies → ~17MB CSV. At 10,000 movies → ~800MB. Running on a student laptop, 1,496 was a practical upper bound.

2. Dataset intersection: Movies needed to exist in both TMDB (for metadata) and MovieLens (for user ratings to build the correlation matrix). The intersection of well-rated, well-known films with both metadata and rating history naturally clustered around ~1,500 entries.

Production Fix Use sparse matrix representation (only store non-zero correlations). Or switch to an embedding-based approach where correlation computation is replaced by ANN search — scales to millions of items.
Q
How did you pre-process the tags column for movies? ▼

The tags column is a denormalized NLP feature engineered offline in a Jupyter notebook, then saved to movies5_1496.csv. Construction:

  • genres: List values joined, lowercased
  • keywords: List values joined, lowercased
  • overview: Space-tokenized, lowercased
  • cast: Names with spaces removed ("Tom Hanks" → "TomHanks") — prevents "Tom" from matching unrelated entries
  • director: Same treatment as cast
  • production_companies: Same treatment

Everything concatenated into one lowercase string. Removing spaces from names ensures the full name is treated as one token by the vectorizer — a deliberate NLP design decision to improve specificity.

Q
Why random sampling for the initial item display? ▼

Movies: head(50).sample(16) — top 50 by vote_average, then random 16. Songs: head(100).sample(16). Books: similar.

Without sampling, every user would see the exact same 16 items — always Toy Story, The Dark Knight, etc. Random sampling from the top N ensures variety while keeping quality high. Users are more likely to have seen and be able to rate items from the top tier.

This is a simple form of exploration-exploitation tradeoff: exploit the high-quality items (top 50/100) while exploring which ones to show (random sample).

Known Anti-Patterns & Limitations

Owning these shows engineering maturity. Know them cold.

Q
Global state for recommendations — how would you fix it? ▼

The globals were a shortcut for a single-user demo. The fix is simple: return recommendations directly in the POST response.

# Current (broken):
movies_recommend_final = compute_recommendations(ratings)
return jsonify({}), 201  # client must GET separately

# Fixed:
results = compute_recommendations(ratings)
return jsonify(results), 200  # return inline, no global needed

This also eliminates the GET /movie_result, GET /book_result, GET /song_result endpoints entirely.

Q
No feature normalization for songs — how bad is it? ▼

Significant. duration_ms has values around 200,000. valence has values 0–1. When computing Manhattan distance, the contribution of duration_ms is ~200,000x larger than valence. Essentially, the distance is almost entirely determined by how similar the song durations are.

Two songs with identical danceability, energy, and valence but different durations could end up far apart. Two songs with opposite moods but similar durations end up close.

The fix is one line of scikit-learn:

from sklearn.preprocessing import StandardScaler
features_scaled = StandardScaler().fit_transform(features)
Q
Flask re-reads CSV files on every request — no caching? ▼

Actually, the CSVs are read once at import time into module-level pandas DataFrames in each module (Movie.py, Song.py, Book.py). So they're cached in-process for the lifetime of the Flask server. Each request does not re-read disk — it queries the in-memory DataFrame.

What's not cached: the recommendation computation itself. Every POST re-runs the vectorizer, similarity computation, etc. For a single-user system this is fine. For production, cache recommendation results by input signature in Redis.

Q
POST /filter is not RESTful. What's wrong with it? ▼

REST convention: GET for reads (idempotent, cacheable, bookmarkable), POST for writes (creates/mutates state).

Filtering movies is a read operation — it doesn't create or modify anything. It should be:

GET /movies?genres=Drama,Thriller&limit=16

The current POST /filter approach: mutates a global filtered_movies variable, requires a second GET /filtered request to retrieve results, is not idempotent (calling twice with same params is fine, but the pattern implies mutation), and cannot be bookmarked or shared as a URL.

The fix also eliminates the GET /filtered endpoint entirely.

Q
Dead code in Song.py (addFeaturesColumn / KMeans). Why is it there? ▼

Vestigial from an earlier implementation. It's defined, imports KMeans, but is never called in the recommendation path. It should have been deleted before submission.

In a code review, this would be flagged immediately: dead code adds cognitive overhead, can confuse future maintainers ("is this used somewhere? why is it here?"), and suggests incomplete cleanup.

I'd delete it. If the clustering idea is worth preserving as a future optimization, it belongs in a comment or a separate feature branch — not as dead production code.

Q
What other improvements would make this production-ready? ▼
  • No auth: No user accounts, no session management. All state is shared globally.
  • No input validation: POSTed ratings aren't validated (could send non-numeric ratings, out-of-range values, injection payloads).
  • No error handling: If a rated book title isn't found in the pivot table, the code may fail silently or crash.
  • No logging or observability: No structured logs, no metrics, no tracing.
  • Hardcoded data paths: CSV paths are relative to the Flask working directory — fragile if run from a different directory.
  • No rate limiting: The recommendation endpoints could be hammered.
  • Poster images via Amazon CDN URLs: External dependency — if Amazon changes URLs, all poster images break.

Critical Engineering Issues (Fix These Before Any Algorithm Change)
1
Models are re-trained on every single request ▼

The single highest-impact fix is not an algorithm change — it's an architectural one.

Books: Book.runKNN() fits a KNN model on a 674×29,782 sparse matrix from scratch on every POST to /recommendbook. Movies: getSimilarity() recomputes a full 1,496×1,496 cosine similarity matrix on every /recommendmovie POST. Every GET endpoint re-reads CSVs from disk.

Fix Load all datasets and pre-compute all models once at Flask startup as module-level variables. Estimated speedup: 10–50× for book recommendations, 5–10× for movies. 
# app.py — run once at startup, not per-request
MOVIES = Movie.readCSVMoviesBackend()
CORR   = Movie.readCSVCorr()
SIM    = Movie.getSimilarity(MOVIES)
SIG, IDX = Movie.getSigIndices(MOVIES)
BOOKS  = Book.readCSVBooks()
PIVOT  = Book.readCSVPivotTable()
KNN    = Book.runKNN(PIVOT)
SONGS  = Song.readCSVSongs()
2
Song distance is a Python loop — 50–100× slower than it needs to be ▼

recommendOneSong() in Song.py iterates 8,010 rows in pure Python, calling np.absolute() per cell. With 3 rated songs, that's 24,030 interpreted iterations.

Fix — one line replaces the entire inner loop Replace the tqdm loop with a vectorized numpy operation. 
feature_cols = [c for i, c in enumerate(data.columns) if i not in [0,1,2,3,4,5,18]]
distances = np.sum(np.abs(data[feature_cols].values - song_row[feature_cols].values), axis=1)

Estimated speedup: 50–100× with zero algorithm change.

3
Race condition in global state — two simultaneous users overwrite each other ▼

movies_recommend_final, songs_recommend_final, and books_recommend_final are module-level globals mutated by POST handlers and read by subsequent GET handlers. If two users POST simultaneously, User B's POST overwrites User A's results before User A's GET reads them.

Fix Return results directly from the POST response body. Eliminate the two-phase POST→GET pattern entirely. This makes the API stateless and safe for concurrent users.
4
KMeans in Song.py is computed but never used (dead code) ▼

addFeaturesColumn() fits KMeans with 10 clusters on normalized audio features and adds a features column to the songs DataFrame. However, this column is never referenced in recommendOneSong() or recommendSongs(). The clusters were the intended foundation for two-stage retrieval but were never wired in.

The intended fix was already planned Filter candidates to the same cluster before distance computation. Reduces O(8,010) to O(~801) average case — the work was done, just never connected.
Algorithm Improvements by Domain
▲
Movies — Replace Pearson Correlation CF with ALS Matrix Factorization ▼

Problem with current approach: The Pearson correlation matrix was pre-computed on a static dataset. It cannot incorporate new ratings without a full recompute. Pearson is also sensitive to high variance on small sample sizes (users who rate few items).

Better: ALS (Alternating Least Squares) Matrix Factorization

  • Factorizes the user-item matrix into k latent factor matrices U (users × k) and V (items × k)
  • Handles sparsity far better than Pearson correlation — movies with few shared raters still get positioned in latent space
  • Supports incremental updates without full recompute
  • For explicit ratings: Surprise library's SVD++ outperforms plain SVD
  • Fits 1,496 movies in under 1 second on CPU with the implicit library
SOTA 2024–2025 LightGCN (He et al., 2020) — models users/items as a bipartite graph and propagates embeddings via lightweight graph convolution. State of the art on MovieLens benchmarks. Overkill for 1,496 movies but the correct production answer.
▲
Movies — Replace CountVectorizer + Sigmoid Kernel with Sentence Transformers ▼

Problem: Two content methods (CountVectorizer + cosine, TF-IDF + sigmoid kernel) both operate on the same tags field — they are not truly orthogonal. Bag-of-words loses semantic meaning: "Action thriller" and "psychological suspense" have zero word overlap despite being semantically close. The sigmoid kernel over TF-IDF has no principled theoretical advantage for recommendation and can produce non-intuitive negative similarity scores.

Better: Sentence Transformers (all-MiniLM-L6-v2)

  • Encode the tags field into 384-dimensional dense semantic vectors once offline
  • "Action thriller with psychological tension" becomes semantically close to "crime drama with mind games" — even with zero word overlap
  • Replaces both content methods with a single, simpler, more accurate approach
  • Pre-computed embeddings stored as .npy file (~4.4 MB for 1,496 movies) — loads in milliseconds at startup
# One-time offline embedding
from sentence_transformers import SentenceTransformer
model = SentenceTransformer('all-MiniLM-L6-v2')
embeddings = model.encode(movies['tags'].tolist())
np.save('movie_embeddings.npy', embeddings)
▲
Books — Replace Dense Pivot → KNN with TruncatedSVD + FAISS ▼

Problem: The 674 × 29,782 pivot table is extremely sparse. Two books with zero users in common have cosine distance of 1.0 (maximally dissimilar) — recommendations for rarely-rated books are effectively random. The 76.7 MB dense CSV is loaded per-request and KNN is refitted from scratch each time.

Better: TruncatedSVD → FAISS

  • TruncatedSVD(n_components=50) on the sparse pivot — 50 latent factors capture most variance, positions all books in a shared latent space even with zero shared raters
  • Store the resulting 674×50 item matrix and query with FAISS IndexFlatL2
  • Reduces memory: 76.7 MB CSV → ~270 KB float32 matrix
  • Speeds up lookups: microseconds vs. full KNN refit
  • Also partially solves sparsity — the "zero overlap = maximum distance" problem disappears
Also add a content fallback Book title + author TF-IDF as a fallback when a book is not in the pivot table. Currently this path crashes with an uncaught exception.
▲
Songs — Wire in the KMeans Clusters + Use FAISS ▼

The KMeans (k=10) was already fitted but never connected to the recommendation logic. The intended two-stage retrieval was: find cluster → distance within cluster only.

Immediate improvement (uses existing code): Filter candidates to the query song's cluster before distance computation. Reduces O(8,010) to O(~801) average case — roughly 10× faster, same algorithm.

Better: FAISS IndexFlatL1

  • Exact Manhattan distance nearest-neighbor queries in microseconds for 8,010 songs in 12 dimensions
  • Drop-in replacement for the manual loop
  • Same results, ~1000× faster
import faiss
index = faiss.IndexFlatL1(12)
index.add(songs[feature_cols].values.astype('float32'))
D, I = index.search(query.astype('float32'), k=11)  # top-11, exclude self
What I Would Add (Not Just Replace)
+
Session Persistence — Enable Real Personalization Over Time ▼

The system is entirely stateless. Ratings are sent as POST body, processed once, and discarded. The same user's preferences cannot accumulate. The system cannot improve for a user after their first session.

Fix: SQLite + session tokens Store user ratings in SQLite keyed by a session token (set as a cookie). On subsequent visits, load previous ratings and append new ones. No algorithm change needed — just feed the accumulated history into the same existing recommendation logic.
+
Fix Popularity Bias in Discovery — Surface Long-Tail Items ▼

All three discovery endpoints use head(50).sample(16) — a movie ranked 51st is permanently invisible. The top-50 cap artificially restricts the candidate pool and creates a feedback loop where popular items get rated more, making them appear even more popular.

Fix: Weighted sampling Replace head(50).sample(16) with a weighted sample where items outside the top-50 have non-zero probability (e.g., inverse-rank weighting). This surfaces items ranked 51–200 and improves discovery diversity.
+
LLM Re-ranking with RAG — The Most Publishable 2024–2025 Addition ▼

The current system returns items with no explanations. Users don't know why something was recommended.

Two-stage architecture with LLM re-ranking:

  • Stage 1 (Retrieve): Use existing algorithms (or FAISS) to get top-30 candidates fast
  • Stage 2 (Re-rank + Explain): Send candidates + user ratings to an LLM with a prompt like "Given a user who liked X, Y, Z, rank these 30 candidates and explain why the top 5 fit"

Papers: TALLRec (2023), LLaMA4Rec (2024), RecGPT (2024). This is the frontier of recommendation research as of 2024–2025.

Tradeoffs API cost (~$0.001/request with Claude Haiku or GPT-4o-mini), 1–3s latency, hallucination risk without RAG grounding to your actual dataset.

Ideal v2 Architecture
Two-phase offline + online design Pre-compute everything expensive offline. Serve only fast lookups at request time. 
── Offline pipeline (runs once / on data update) ──────────────────
→ Sentence transformer embeddings for movies / books / songs tags
→ ALS or LightGCN training on rating data
→ TruncatedSVD (k=50) on book pivot matrix
→ FAISS indices built from all embeddings
→ Saved as .npy / .faiss files to disk

── Flask startup (runs once) ───────────────────────────────────────
→ Load pre-built FAISS indices into memory
→ Load pre-trained model weights
→ Ready to serve in <1 second

── Request time (per user) ─────────────────────────────────────────
→ Encode query vector (fast inference)
→ FAISS k-NN lookup (microseconds)
→ Optional: LLM re-rank top-N candidates
→ Return results in <100ms

This is the same two-tower architecture used by YouTube, Spotify, and Pinterest at scale — implemented at BE project scale.
